# 性能測定と最適化

## 通常版と速度優先版

- 最適化は速度優先版で試してよい。採用する改善は同じ変更で通常版の原本にも反映し、入力検査・所有権・容量保護・例外時の契約を維持する。速度優先版固有の前提を使う場合は、通常版に適した実装で反映し、両版で正しさと速度を確認する。生成済みファイルを直接編集せず、原本または生成器を改修して全8版を更新する。

## 最適化する範囲

- Library CheckerのVerify提出コードはmain・入出力・型変換・問題ごとの計算手順を含むプログラム全体を最適化対象とし、Codexの検討・測定後にClaudeへ引き継ぐ。正しい全入力での動作とライブラリの公開APIを保ち、問題の前提を利用した最適化は根拠と対象範囲を記す。Library Checker以外（yukicoder・AtCoder・AOJ）は正しさの検証を主目的とし、最適化はライブラリ本体だけを対象とする。main・入出力の個別チューニングや最速記録の追求は行わず、共通入出力と読みやすいAPI呼び出しを基本とする。問題の制約内で解くために必要なアルゴリズムやデータ構造は用いてよい。使用例は読みやすいcin/coutを基本とする。

## 測定条件と判定

- 最適化の測定では、本体だけの効果と、main・入出力を含む全体の効果を区別する。本体だけの比較は同じ問題・main・入出力・コンパイラ・検査設定で行う。全体比較でも入力・環境・コンパイラ設定をそろえる。他者の提出時間や過去の通常入出力による記録は、条件を保って区別する。
- 性能CIではPRのベースコミットと変更後を同じジョブで交互に計測する。正答と測定件数を照合し、各ライブラリの最悪ケースが再測定でもGitHub標準ランナー用の許容幅を超えたときに性能退行で失敗とする。許容幅は[CIの品質検査](../ci_quality.md)を参照。比較不能なケースは理由と件数を表示する。
- `Audit/Performance/`の測定記録は、同じライブラリ・操作・比較範囲を新しい測定で確認したら、最新の記録に更新する。測定条件・比較元と比較先のSHA・結果・採否を残し、置き換わった明細や一時ログを削除する。ライブラリ単体とプログラム全体など別の目的の測定や、現在の性能判定・SHA照合に必要な根拠は保持する。

## 変更後の検証と再提出

- 最適化後に本体・main・入出力のいずれかを変更した場合は、影響するVerifyコードを生成・ローカル検証して再提出する。Codex/Claudeの実施記録と判定を提出ソースのSHA-256へ結び付け、旧版のACを変更後のコードへ引き継がない。
- 着手前と採用後の提出コードのSHA-256、正しさの照合と性能測定の根拠を保存する。記録手順は[最適化の記録](../../Verify/optimization/README.md)を参照する。
