# API文書と使用例

## 公開APIの説明

- コメント・説明は短い日本語。APIの前提、計算量、戻り値は正確に記す。
- 自明でない公開操作は、コード先頭のAPI一覧とDocumentの両方に計算量を記す。N・Mなどの変数の意味を示し、必要に応じて前処理・通常操作・償却計算量・出力件数に比例する費用を区別する。共通の記法や型の前提は先にまとめてよいが、Documentでは各関数の節に対応する制約と計算量を短く記す。
- 新規追加・改修するライブラリのDocumentと生成ページは、短い概要の後に「関数ごとの見出し・シグネチャ・短い説明・制約・計算量」の順で揃える。API操作は表にまとめず、別の関数は別見出しにする。同名のオーバーロードは同じ節に複数のシグネチャを並べ、違いを短く説明する。型・設定・コールバックの共通説明は箇条書きでまとめてよい。
- シグネチャは`text`のコードフェンスで示し、実行する使用例の`cpp`と区別する。戻り値・引数型・テンプレート引数・既定値・`const`等を実装と照合し、型の別名も利用側が理解できるよう説明する。削除・非公開の宣言を利用可能なAPIとして載せず、対象ファイルに含まれる操作だけを説明する。同梱する型の操作も確認し、通常版・圧縮版・用途別版の違いを混ぜない。
- 説明の簡潔さと構成は`Document/lis.md`・`Document/rolling_hash.md`を目安にする。固定の行数へ合わせず、全公開APIと重要な制約・例外・所有権・参照の寿命を保つ。短い文書を水増しせず、同じ説明や内部最適化の詳述を繰り返さない。生成ページは使い方を先に置き、検証結果やソースのAPI注記は本文の後ろに折り畳む。
- 専門用語やテンプレート引数は、利用側で何を渡し、何が返るかが分かる言葉で短く説明する。使用例は代表的な操作を数行から十数行で示し、完全なプログラムは`Examples/`へリンクする。長い入門講座、同じ説明の繰り返し、利用に直結しない内部最適化や測定条件の羅列はDocumentへ追加しない。追加・改修後は参照文書と比べ、長さと必要な操作の探しやすさを確認する。
- 公開APIの説明は、各ソースの冒頭（ライセンス・出典の直後、includeより前）の一か所へまとめる。対応するDocumentへのリンクを添え、型・関数群ごとに引数・戻り値・計算量・重要な前提を短く記す。オーバーロードも区別し、各定義の前へ同じ説明を重複させない。内部実装の注釈は必要な位置に残す。

## READMEの役割

- READMEは概要・使い方・資料への案内に絞る。変更履歴や長い測定記録を書かず、Documentにも変更履歴を書かない。
