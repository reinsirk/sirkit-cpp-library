# Union Find 414076の確認と追加比較

[414076](https://judge.yosupo.jp/submission/414076)で全18ケースAC・16msを確認した。提出本文は、Submission注記・空行・行末空白・改行形式のみを正規化すると、現行の本体・main・共通入出力と一致する。本体SHA256は`dffd5844ef1e0d00d3325dd3e384eaf552e32352696c04cdd364091dc58c32a0`。

旧412615のAC・10msを履歴として保持した。大半のケースは±1ms以内だが、`path_00`だけ5→16ms。前回改修前のローカル旧版と現行版を、GCC15.2/15.3・通常/native・P-Core12固定・同じmain/I/Oで31反復したところ、path_00の中央値は約4.15〜4.45ms→4.16〜4.37ms、新/旧0.980〜1.031だった。オンラインの約3倍の増加は再現していないが、原因は未確定。ローカル旧版のSHAとオンライン旧版のSHAは区別して記録した。

## 追加候補

全てC++23・O2・検査省略で比較した。mainの計算手順・共通入出力を変えず、API測定も前回と同じ別翻訳単位のハーネスを使用した。旧新の順序を固定seedでshuffleし、同じpath/inodeで実行。同じバイナリのcontrolも加えた。

| 候補 | 結果・判断 |
|---|---|
| 勝者ごとに分岐して書戻し | 大規模ランダム結合が約5〜6%増。不採用。 |
| `param.data()`から親配列を参照 | GCC15.2/15.3とも混合・照会関数の機械語が現行と同一。効果なし。 |
| 上の2案の組合せ | 混合関数の機械語は書戻し分岐案と同一。不採用。 |
| 第二引数の先読み | 一部の結合は短縮するが、大規模な星形の失敗結合などで約5〜19%増。不採用。 |
| 書戻し位置を非所有ポインタで保持 | GCC15.2の中規模混合で約9%短縮が再現する一方、GCC15.3の大規模同頂点への失敗結合で約3〜5%増、中規模の一部で約11%増。不採用。 |
| 条件代入とXORで勝者・敗者を選択 | 結合・混合に改善がある一方、GCC15.3の大規模同頂点への失敗結合で約6%増が再現。不採用。 |

最後の2候補は、懸念が出たAPI条件を15反復し、同じmainで公式18ケースを9反復した。mainのケース別中央値の合計比は、ポインタ保持案が0.994〜1.008、勝者選択案が0.993〜0.997。提出全体の短縮は小さく、大規模の別操作に残る後退を引き換えに採用する根拠は得られなかった。

候補の独立参照検査44構成は全成功。先読み案はClang・検査有無・native・ASan/UBSanも含む。最後の2案はGCCの代表ID・サイズ・成分列挙・未圧縮の深い経路への失敗結合を検査有無で照合した。機能検査に成功しても、速度の採用基準とは分けた。

API比較は計10584実行、公式入力のmain比較とpath確認は計4452実行。出力・API結果を独立参照と照合した。controlにも揺れがあるため、全ての小差を実装によるものとは断定しない。

**本体・main・共通入出力を414076のAC版のまま維持する。追加の再提出は不要。** 提出コードの注記は最新URLだけに揃え、再提出待ちは解消した。アルゴリズムや既存の高速化を変更しない。
