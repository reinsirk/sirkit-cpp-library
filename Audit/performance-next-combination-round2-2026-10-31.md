今回は全候補を不採用とし、`Algorithm/next_combination.cpp`・main・共通入出力を維持した。追加の再提出は不要。現行SHA-256は `1b7993319b8d817c341993008c0948aa3a0a25db89b9fa83eac33151a06f7d4a`。旧記録の4146f3bc版との差は、API説明コメントを冒頭へ移したもので実装差ではない。

## 比較した案

現行版は除算を使わず、列挙の終端を開始時に計算し、k=1以外のマスク更新を1回の右シフトへまとめている。過去に不採用だった単項nextのbranchless化・一般列挙のAND-NOT化は再試行していない。

| 案 | 結果と判断 |
| --- | --- |
| k=1だけループを分離し、更新式は現行XORを維持 | GCC通常の大規模mainは約2.7%短縮だが、提出条件に近いnative設定は約4.5%増で不採用 |
| k=1の分岐配置を調整 | 同native設定の大規模mainが約8.2%増で不採用 |
| k=1と終端の分岐配置を調整 | 同約7.2%増で不採用 |
| 幅超過をhighの計算直後に判定 | GCCのランダム照会は約9〜14%短縮するが、連続照会やClang等に退行 |
| 幅判定をtail後へ戻し、判定対象はhighへ | GCC32bit連続列挙は約11%短縮するが、Clang32bit等で退行 |
| 8bitやClangへ旧処理を残す | 単独のmain/for_each等のコードは保持できたが、混在callerの退行が残る |
| 条件構文の整理、元のnext計算を残す最小変更 | 同じ混在callerの退行を解消できず不採用 |

幅判定の案は、Gosper更新のhighと最終nextの最上位setbitが同じという性質を使う。0・桁あふれ・全幅シフト・失敗時のmask不変性は保った。候補はconstexprや独立参照の照合にも通ったが、正しさだけを採用理由にはしない。

特にGCCだけへ限定した実験名 `final.hpp` の候補は、21反復で32bit幅付き連続列挙を約11%、64bitを約2〜4%短縮した。しかし複数APIを同じ関数へ含むベンチマークでは、GCC/nativeの16bit列挙や32bit k=31の依存ハッシュvisitorに最大約20%の増加が残った。k=31の列挙自体は32回の小規模条件である。for_each定義は不変で、呼出元全体のコード生成の影響が考えられるが、具体的な命令上の原因は断定しない。独立プログラムの一致だけを根拠に、この退行を無視していない。

## 測定条件と入力

Core i9-14900KのP-Core CPU12へ固定。コンパイル・正誤検証はCPU4。GCC15.2のC++23/O2通常設定、gnu++23/O2/native・自動変数ゼロ初期化等のAtCoder関連設定、Clang21の標準C++23/O2で比較した。全リンク条件やAtCoder実機を再現したものではない。計時は検査省略、main・入出力は全候補で同じ。明示的なSIMD・CPU判定・拡張型は追加していない。

APIは8/16/32/64bitのfor_each、単項next、幅付きnext、int版を含む77条件。合計または依存ハッシュのvisitorを使い、小規模・幅端・k=0/1/n・多い組合せを区別した。基本比較は5反復、最終候補は21反復、構文調整と最小変更は11反復。同一ソースの別ビルドを対照に含め、順序を乱して同じ実行パスで測定した。

APIは入力構築を除くprocess CPU時間、mainは入力・出力・callbackを含む子process CPU時間。mainは各7反復。大規模mainの比率はM=28の13条件の中央値合計から求めた。小規模で起動時間が支配的なmainの差は採否の根拠にしない。

[ABC328 E](https://atcoder.jp/contests/abc328/tasks/abc328_e)の公式3サンプルと、従来の制約内入力・辺順/頂点順の置換を合わせた19入力を復元した。各入力SHAは旧記録と一致。期待出力は、辺部分集合やDSUを使わないPrüfer列の全ラベル付き木列挙で独立に計算し、19件全ての出力SHAが旧記録と一致した。これは公式テストケースの測定ではない。
